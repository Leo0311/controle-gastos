## 2. Bugs reais encontrados em uso (fora do plano original)

**Recorrente não salvava pelo diálogo rápido — `805b7d6`.**
No "Novo gasto", marcar "Tornar recorrente" e salvar não gravava nada; a mensagem
"Gerar para os próximos meses deve estar entre 1 e 12." aparecia depois, e **na
tela de Gastos**, não no diálogo. Causa raiz: o `gasto-form-dialog` (caminho do
checkbox) nunca teve o campo `mesesGerar` / "Gerar para os próximos meses" no
form — o backend valida `1..12` e rejeitava. O diálogo dedicado
(`gasto-recorrente-form-dialog`) sempre teve o campo; só o caminho do checkbox
ficou de fora quando o checkbox foi adicionado. Lição gravada na skill
`frontend-angular` + memória `project_dois_dialogos_recorrente` (um campo
validado no backend tem que existir nos **dois** formulários que criam a mesma
entidade).

**Falta de loading ao salvar recorrente/parcelada + hint vazando — `1810354`.**
Salvar uma recorrência gerando N meses (ex.: 12) demorava segundos sem nenhum
indicador e com os botões ativos (risco de duplo submit). Além disso o `mat-hint`
"Deixe em branco para não gerar" vazava por cima do label "Orçamento (opcional)".
Causa raiz do visual: padding no container que colapsa na animação de altura
(`overflow: hidden` não encolhe o próprio padding — armadilha de CSS já
documentada na skill). Fix: spinner + botões desabilitados durante o save nos
dois diálogos; hint reposicionado num filho do container.

**Falta de foco automático no campo obrigatório inválido — `c4cccf8`.**
Clicar em "Salvar" com um campo obrigatório vazio não focava nada — se o campo
estivesse fora da área visível do diálogo, o usuário não via por que não salvou.
`shared/form-utils.ts` ganhou `focarPrimeiroInvalido()` genérico: percorre os
controles na ordem em que aparecem no DOM, foca e rola até o primeiro inválido.
Aplicado nos dois diálogos de gasto no momento do submit.

**Exclusão em cascata de recorrentes — `7b5ba9e` (decisão de produto, não bug).**
Antes: excluir um lançamento de recorrência pela aba Gastos apagava só aquele
gasto; excluir o molde pela aba Recorrentes apagava só os gastos `>= hoje`. Agora
os dois pontos fazem a mesma coisa: apagam **todos** os lançamentos da
recorrência (passados e futuros) + o registro, numa transação. Ponto único
`GastoService.excluirRecorrenciaEmCascata(recorrenteId, usuarioId)` (`@Transactional`,
valida dono → `DELETE` de todos os gastos em 1 query → `DELETE` do registro; a
ordem importa porque o FK é `ON DELETE SET NULL`). `ConfirmDialogComponent` ganhou
um modo async retrocompatível (`data.acao: () => Observable`): o diálogo executa a
chamada ele mesmo, fica aberto com spinner + botões travados + `disableClose` até
terminar, e no erro destrava sem fechar. Sem migração de schema (só o comentário
do FK em `schema.sql` foi atualizado).

**Sugestão de categoria apagava subcategoria já escolhida — `00aea0d`.**
No "Novo gasto", se o usuário ignorava a sugestão automática e escolhia uma
subcategoria à mão: (1) o chip de sugestão continuava aparecendo e (2) clicar
nele **apagava** a subcategoria escolhida. Causa raiz: o getter `sugestao` só
escondia o chip quando a combinação sugerida era idêntica à selecionada; e
`aplicarSugestao` setava `subcategoriaId = null` quando a sugestão era
categoria-só. Fix (`sugestao-categoria.ts`, lógica pura): `sugestaoDeveAparecer()`
esconde o chip assim que **qualquer** subcategoria é escolhida; sugestão
categoria-só não mexe numa subcategoria já preenchida; o "x" (dispensar) persiste
até a sugestão mudar de conteúdo (`mesmaSugestao`). Testes novos no getter e no
`aplicarSugestao`.

## 3. Item 2.3 — performance da geração de gastos recorrentes (`e72ffc0`)

Cadastrar uma recorrência com `mesesGerar = 12` (medido local, Postgres 14, via
`spring.jpa.show-sql` + log do `JdbcTemplate`):

| | Round-trips ao banco (geração de 12 meses) |
|---|---|
| **Antes** | **~36** — `1 select usuarios (auth)` + `12 select categorias` (resolvia a mesma categoria 1×/mês) + `1 insert recorrente` + `11 select gastos` (`exists` de duplicata, 1×/mês) + `11 insert gastos` (individuais) |
| **Depois** | **4** — `1 select usuarios (auth)` + `1 select categorias` (resolvida 1× antes do laço) + `1 insert recorrente` + `1 batch insert` de todos os gastos |

As três otimizações: (1) `resolverCategoria` roda 1× em `cadastrar`/`atualizar` e
passa os nomes prontos pro laço (mesmo padrão do `CompraParceladaService`); (2)
numa recorrência **nova** o `exists` de duplicata é pulado (não há gasto nenhum
ainda) — na edição virou 1 query só que traz todas as datas do horizonte; (3)
inserts em lote via `GastoRepository.inserirEmLote` (fragmento custom com
`JdbcTemplate.batchUpdate`) + `reWriteBatchedInserts=true` no pool Hikari.

**Por que não `hibernate.jdbc.batch_size`:** `Gasto` usa
`GenerationType.IDENTITY`, que obriga o Hibernate a fazer um round-trip por
`INSERT` pra ler o id gerado — isso **desliga o batching de INSERT nativo do
Hibernate**, independente de `batch_size`. Por isso o lote foi feito no nível do
JDBC (`batchUpdate`), não via `saveAll` + `batch_size` (que seria inócuo pras
entidades deste projeto). O cold-start do Neon serverless é ortogonal e segue
fora do escopo.
